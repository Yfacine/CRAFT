## 2 작업 시작

CRAFT 루트에서 [초기화 스크립트](../scripts/Initialize-Craft.ps1)로 REA 설정을 생성한 뒤, 그 루트를 Codex 작업 폴더로 열고 주 에이전트에게 요청한다. 주 에이전트가 **MAIN**으로 참여하고, 프로젝트에 등록된 SUB 10개를 필요에 따라 호출한다. 기존 `craft_replica` 이름의 자연어 요청도 MAIN과 `$craft-replica`로 연결한다. 착수 전에 사용할 도구와 연결 경로는 [레퍼런스 목록](references/README.md)에서 확인한다.

> $craft-replica 스킬로 [대상·버전]의 [대체할 업무]를 재현해줘. 원본은 [URL 또는 경로], 허용된 분석 범위는 [범위], 필수 결과물은 [파일 또는 동작]이야. MAIN이 대상 계획을 작성하고 분석·코딩·코드 검토·TF 역할을 배정해줘.

## 3 역할 배정

작성 경로는 `targets/<대상-id>/` 기준이다. MAIN만 `plans/targets/<대상-id>.md`의 배정과 최종 판정을 갱신한다.

| 팀 | 역할 | 착수 입력과 작성 범위 |
| --- | --- | --- |
| 분석 | `craft_reap` | 대상·기능 ID·허용 범위 → `evidence/reap/` 조사 질문 |
| 분석 | `craft_rea` | 인수된 질문·원본 → `evidence/rea/` 관찰 근거 |
| 분석 | `craft_replica_spec` | REA 근거 → `spec/` 기능 계약·인수 사례, 고정 빌드 → `checks/replica-diff.md` 분석 결과 |
| 분석 | `craft_anything` | 허용된 대상 → `evidence/craft/` 재현 방법·비교 근거, 격리된 `work/craft/` 분석 작업 |
| 분석 | `craft_cli_anything` | 대상·입출력 계약 → `evidence/cli/` 자동화 경로·검증 방법 |
| 코딩 | `craft_coder` | 확정 명세 → `app/`, `harness/`, `tests/` 및 지정 빌드 파일. 격리 생성 경로는 `work/implementation/`, 자체 테스트 근거는 `evidence/implementation/` |
| 코드 검토 | `craft_code_review` | 고정 변경분·명세·자체 테스트 → `checks/code-review.md` 코드 결함과 재확인 기준 |
| TF 작업 설계 | `craft_tf_design` | 대상 계획·인계·자원 배정 → `checks/tf-design.md` 누락·중복·충돌 검토 |
| TF 구현 정합성 | `craft_tf_alignment` | 구현 전에는 원본 근거·명세·필수 목록, 후보 단계에는 고정 후보·구현 위치·검증 결과 → `checks/tf-alignment.md` 단계별 검토 |
| TF 품질·인수 | `craft_tf_acceptance` | 고정 빌드·기준값·인수 사례 → `checks/tf-acceptance.md`, `evidence/acceptance/` 실측 결과 |

코딩 담당만 제품 코드와 테스트 코드를 작성·수정한다. 분석 중 실험은 배정된 격리 경로에서 진행하고 제품에 반영할 방법을 코딩 담당에게 인계한다. 코드 검토자는 고정 변경분의 오류 처리·호출 경로·회귀를 보고, TF 정합성 담당은 원본 요구가 명세·구현·검증 사이에서 빠지거나 달라졌는지를 본다.

## 4 인계와 검증 순서

| 단계 | MAIN이 확인할 산출물 | 다음 단계의 착수 조건 |
| --- | --- | --- |
| 1. 범위 초안 | 대상 버전, 허용 범위, 대체 업무, 필수 관찰 목록 초안 | 분석 대상과 허용 범위를 정함 |
| 2. 분석 및 구현 전 확정 | 수락된 원본 근거, 명세, 확정 필수 목록과 기준 버전 | 필요한 사전 검토와 명세·계약 확정을 마침 |
| 3. 구현과 후보 고정 | 코드 리비전, 배포물 지문, 자체 테스트, 독립 검토 배정 | 실제로 실행할 후보와 기준을 고정함 |
| 4. 실측 | 고정 후보의 필수 항목별 실제 결과와 증거 | 결과를 기준과 대조할 수 있음 |
| 5. 수정과 재검증 | 실패 이력, 변경 이유, 영향 사례와 새 후보의 증거 | 영향받은 검토와 실측을 갱신함 |
| 6. 최종 인수 | 필수 목록 대조 결과, 인수 또는 보류 사유 | [인수 판정](#6-인수-판정)의 조건을 충족함 |

### 4.1 범위 초안

MAIN은 대체 업무와 분석 허용 범위를 정하고, [대상계획 양식](04_target-plan-template.md#3-필수-관찰-목록)에 `기능 ID → 인수 사례 ID → 필수 관찰 항목 ID`로 초안을 적는다. 미확정 인계나 자원 충돌 가능성이 있으면 작업 설계 TF를 호출한다.

### 4.2 분석 및 구현 전 확정

- REAP 질문 → REA 조사 → replica-skill 명세를 이어간다. 근거마다 제공자, 소비자, 필수 여부, 인계 리비전과 수락 상태를 기록한다.
- 독립적인 Craft Anything 관찰과 CLI-Anything 자동화 조사는 입력을 확보하고 자원 격리를 확인한 범위에서 병행한다. CLI-Anything의 입출력 계약 분석은 필요한 명세를 받은 뒤 시작한다. 신규 대체 범위에는 다섯 레퍼런스의 역할과 증거를 남긴다.
- MAIN은 필수 근거를 수락하고 원본 근거, 초기 상태·입력, 기대값과 비교 규칙을 목록에 연결한다. 신규 대상이나 파일 형식·입출력 계약 변경은 정합성 TF가 원본 근거·명세(계약)·필수 목록으로 사전 검토한다. 후보·구현 위치·실측 결과는 후보 단계에서 사용한다.
- MAIN은 목록·기준 버전과 명세·계약을 확정하고 [G01 구현 착수](02_gates.md#2-단계별-gate) 판정과 선행 근거를 대상계획에 기록한다. G01을 통과한 범위부터 코딩을 배정한다. 부모 이력 로딩 오류가 나면 이력 상속 없이 같은 배정과 입력을 전달한다.

### 4.3 구현과 후보 고정

코딩 담당은 자체 테스트 후 코드 리비전 또는 파일 지문, 해당 코드로 만든 배포물의 식별자·지문, 명세·인수 기준·테스트 버전, 재현 명령을 제출한다. MAIN은 이를 후보 기록으로 고정한다.

모든 코드 변경에는 별도 코드 검토 담당을 배정한다. 요구 추적에 영향이 있으면 정합성 TF가 원본 근거와 확정 기준을 고정 후보의 구현 위치·검증 결과까지 추적한다. 배정할 때 자체 테스트 결과와 독립 실측 결과 중 필요한 입력과 제공 시점을 구분한다. 독립 실측이 필요한 검토는 G02를 거친 실측 결과를 받아 G03 전에 마친다.

### 4.4 실측

MAIN은 후보와 실행 권한을 확인해 [G02 실측 착수](02_gates.md#2-단계별-gate)를 대상계획에 기록한다. G02를 통과하면 품질·인수 TF는 승인된 환경과 초기 상태에서 고정 배포물을 실제 사용자 진입점으로 실행한다. 관찰 항목별로 실제 배포물 지문, 기준 버전, 실행 환경·입력과 증거를 [대상계획의 실측 결과](04_target-plan-template.md#42-실측-결과)에 연결하고 각각 판정한다. 원본과 후보의 환경이 다르면 사전에 정한 허용 조건을 각각 충족하는지 확인한다. [대상 유형별 사례](#7-대상-유형별-검증)

### 4.5 수정과 재검증

- MAIN은 코드 수정은 코딩 담당에게, 명세·근거 정정은 분석 소유자에게 배정한다. 코딩 담당은 테스트 변경 전후와 이유를 제출하고, 입력·관찰 방법 변경과 합격 기대값 변경을 구분한다. 기대값 변경은 분석 담당의 원본 근거를 토대로 MAIN이 확정한다. 이전 기준과 실패 증거를 보존한다.
- 범위·필수 관찰 목록·계약 또는 합격 기대값이 바뀌면 변경 범위의 G01로 돌아가 필요한 사전 정합성 검토와 기준 확정을 거친다. 기존 G01 기준이 유효한 코드 수정은 그 근거를 재사용한다. 새 후보는 다시 고정하고 G02를 판정한 뒤 독립 실측한다.
- 새 후보의 기존 실패·영향 사례부터 확인하고, G03 전에 현재 후보에 필요한 필수 증거의 공백을 모두 채운다. 작은 코드 변경도 독립 코드 검토와 영향받은 사용자 진입점 실측을 거친다.
- 원본 버전·입력·초기 상태·기대값이 유효한 원본 근거와 영향 밖 분석은 적용 범위를 기록해 재사용한다. 복제품 실측은 실행한 배포물·기준 버전·실행 조건에 귀속한다. 이전 후보 결과는 이력과 영향 판단에 사용한다.

### 4.6 최종 인수

MAIN은 구현 전에 확정한 필수 목록 전체를 실제 결과와 대조하고 [인수 판정](#6-인수-판정)을 기록한다.

## 5 공유 자원과 작성 경로

- 동시 배정 전에 작성 경로를 정규화하고 동일 경로와 상하위 경로의 소유권이 겹치는지 확인한다. 충돌하면 경로를 분리하거나 MAIN이 담당과 사용 순서를 재배정한다.
- GUI, 브라우저 프로필, REA 세션, 포트, 캐시, 빌드·출력 폴더와 데이터는 격리를 확인한 범위에서 병렬 사용한다. 공유 자원의 경우 MAIN이 사용권 보유자, 승인된 조작, 입력 사본, 사용 순서, 초기화 방법과 반환 확인을 배정한다. 다음 담당자는 반환과 초기 상태를 확인한 뒤 착수한다.
- 동시 호출 수는 독립 작업과 세션 여유에 맞춘다. 역할별 경로 배정은 작업 지침으로 관리하고 실행 환경의 격리는 별도로 설정한다.

## 6 인수 판정

MAIN은 [02 Gate의 G03 최종 인수](02_gates.md#3-최종-인수-판정)를 적용한다. 최종 판정은 대상계획 [7.1 Gate 판정 기록](04_target-plan-template.md#71-gate-판정-기록)의 G03 행에 남기고, [7.2 인수 근거](04_target-plan-template.md#72-인수-근거)에서 현재 행과 증거를 참조한다.

대상 계획은 `plans/targets/<대상-id>.md`, 구현과 근거는 `targets/<대상-id>/`에 둔다. 사용자가 다른 경로를 지정하면 계획에 기록한다. 도구별 호출은 [레퍼런스](references/README.md)를 사용한다.

## 7 대상 유형별 검증

| 대상 유형 | 원본 기준값 | 복제품 인수 사례 |
| --- | --- | --- |
| 웹 앱 | 브라우저의 정상·오류 흐름과 다운로드 결과 | 같은 입력으로 UI 흐름을 실행하고 해당 백엔드 결과도 확인 |
| 데스크톱 앱 | 실행 버전, 열기·수정·저장·재열기 결과 | 설치된 복제품에서 저장 파일·메타데이터와 앱 종료 후 새 프로세스에서 재열기한 상태를 따로 대조 |
| CLI·파일 변환기 | 명령, 종료 코드, 표준 스트림, 생성 파일 | 배포된 명령에서 정상·오류 입력을 실행해 종료 코드, 표준 출력·오류, 파일 형식·내용, 부분 파일과 기존 출력 상태를 각각 대조 |

여러 유형의 실제 인수 사례를 완료한 뒤 범용 실행 검증을 판정한다.

## 8 CRAFT 자체 보완과 배포

평소에는 [Yfacine/CRAFT](https://github.com/Yfacine/CRAFT)의 `main`을 최신 작업 기준으로 사용한다. 정식 배포본은 해당 버전의 Release 태그, 전체 ZIP과 SHA-256으로 식별한다. 사용자가 로컬 경로를 지정하거나 특정 버전을 요청하면 해당 범위를 우선한다.

1. **가져오기.** `yfacine/craft 다운받아줘`는 최신 `main`을 Git 작업본으로 가져오는 요청이다. 사용자가 지정한 새 폴더나 빈 폴더에 직접 받는다. 경로를 생략하면 Windows에 설정된 다운로드 폴더 아래 `CRAFT`를 사용한다. 기본 폴더가 이미 사용 중이면 같은 다운로드 폴더 안에서 `CRAFT-2`, `CRAFT-3` 순으로 빈 이름을 고른다. 지정 경로에 파일이 있으면 기존 파일을 보존하고 경로 상태를 사용자에게 알린다. 시작 커밋과 실제 작업 경로를 기록한다. 특정 버전의 Release ZIP은 지정한 폴더에 저장하고, 위치를 생략하면 Windows 다운로드 폴더에 저장한다. 같은 이름의 ZIP이 있으면 기존 파일을 보존한다.
2. **보완과 검증.** 보완 계획서에 따라 작업 브랜치에서 수정한다. 요청 범위와 변경 목록을 대조하고 영향받은 진입점을 검증한다. 버전 업데이트가 포함되면 README의 버전·기준일과 CHANGELOG의 문제·원인·조치·검증 근거를 맞춘다. 프로젝트별 결과물, 로컬 생성 설정, 임시 파일이 공개 변경에 섞이지 않았는지 확인한다.
3. **GitHub 반영.** 사용자가 업로드를 요청한 경우에만 원격 `main`을 다시 확인하고, 검증한 변경을 반영한다. 원격에 새 변경이 있으면 먼저 통합하고 영향 범위를 재검증한다. 충돌이 해결되지 않거나 필수 검증이 실패하면 반영을 보류하고 작업본을 보존한다.
4. **버전 공개와 원격 확인.** 새 버전 공개가 요청되면 확정 커밋에서 태그와 전체 ZIP을 만들고 SHA-256 체크섬과 함께 Release에 올린다. 원격 `main`과 태그가 기대한 커밋을 가리키는지, 공개 Release에서 받은 ZIP과 체크섬이 검증한 배포물과 일치하는지 확인한다. 일부만 반영됐으면 완료된 단계와 보류된 단계를 구분하고 같은 커밋과 산출물을 기준으로 재개한다.
5. **작업 종료.** 작업 폴더 정리는 사용자의 요청에 따른다. 원격 반영이 확인되고 로컬에만 남은 커밋, 변경 파일, 미추적 파일, 보관할 자료가 없는지 확인한다. 사용자가 빈 작업 경로를 유지하도록 요청했으면 폴더를 남기고 내용물만 정리한다.

공개가 끝나면 버전, 최종 커밋, Release 링크와 검증 결과를 전달한다. 로컬 반영만 요청된 작업은 [검증 문서](03_verification.md)에 로컬 검증 결과와 원격 작업의 상태를 구분해 남긴다.
